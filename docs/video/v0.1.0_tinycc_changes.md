# TinyCC for ARMv8-M — what changed between yasos.zig v0.0.8 and v0.1.0

**Video 1 of 2.** This covers the compiler submodule (`libs/tinycc`). The OS
side is a separate document.

Submodule range: `cae3a049` → `fb3a6c57`
Wall time: **2026-02-07 → 2026-08-12** (~6 months)
31 commits, 7 of them squashed PRs.

---

## The one-line version

> At v0.0.8 this was still Fabrice Bellard's TinyCC with an ARM Thumb backend
> bolted on: no IR, no optimizer, no register allocator, direct AST→machine-code
> translation. At v0.1.0 it is a single-target optimizing compiler with a
> three-address IR, SSA form, an SSA register allocator, ~180 optimization
> passes, hardware floating point, and 2100+ test files. Everything else was
> deleted.

## Chapter 1 — The compiler grew a middle (PR #5, February)

*Commit `d1dae418` — "Global register allocator"*

This is the change everything else stands on. Upstream TCC has no intermediate
representation: the parser emits machine code as it goes, which is why it is
fast and why it cannot optimize. This PR inserted a **three-address IR with
explicit register operands** between the front end and the back end.

Screen-worthy: `source/ir/tccir.h` (888 lines of public IR interface), and a
side-by-side of `-dump-ir` output vs the emitted Thumb.

What came with it:
- `source/ir/` — IR core, operand pool, virtual registers, stack layout, CFG,
  SSA construction, two-pass codegen dispatch (dry-run + real-run)
- `source/ir/regalloc.c` (6,006 lines) — an **SSA register allocator**,
  parameterized by a `RegAllocTarget`, with a linear-scan core in
  `source/machine/tccls.c`. Real liveness analysis, which upstream never had.
- Benchmarks and the first real test suites

The commit message is four lines. The diff removed every backend except ARMv8-M,
because carrying six targets through a new IR was not going to happen.

**Talking point for the video:** this is the moment the project stopped being
"a patched tcc" and became a compiler. Everything after this is consequence.

## Chapter 2 — The great restructure

The repo root at v0.0.8 was 161 loose `.c`/`.h` files — upstream TCC's layout.
At v0.1.0 the root holds only build inputs and metadata; all code lives under
`source/`, one directory per module, each with its own `Makefile`, each building
to its own static library:

```
source/
├── include/    tcc.h umbrella header
├── driver/     CLI, TCCState, options
├── frontend/   preprocessor, GAS asm, and gen/ — the former tccgen.c
├── ir/         target-independent IR, CFG, SSA, regalloc, codegen
├── opt/        the optimizer (engine, flat, ssa, analysis, ra, framework)
├── machine/    backend boundary — linear scan, ABI
├── backend/    arch/arm/thumb/, arch/fpu/, generators/
├── obj/        ELF, YAFF, linker, DWARF/STABS
├── memory/     vector, unique_ptr, bitset, bit_matrix containers
└── support/    gdb printers, logging, debug knobs
```

**`tccgen.c` (8,590 lines) → ~50 files** under `source/frontend/gen/`, grouped by
what they do rather than by nothing: `decl/`, `expr/`, `stmt/`, `type/`,
`value/`, `init/`, `op/`, `inline/`, `builtin/`, `store/`, `sym/`, `nested/`.

Note the `builtin/` subtree alone — `call.c`, `chk.c`, `fp.c`, `fp2.c`,
`overflow.c`, `simd.c`, `string.c`, `misc.c`, ~6,900 lines. Builtins that mostly
did not exist before.

**Screen-worthy:** `git log --stat` on the restructure commit, or just
`tree source/ -L 2`.

## Chapter 3 — The optimizer (PRs #7, #10)

Upstream TCC does not optimize. This is now ~86,900 lines and the single largest
subsystem in the compiler — **180 pass source files**.

### Shape

Two phases over the IR, plus pre/post register-allocation passes:

```
frontend → flat-IR passes → SSA construction → SSA passes → RA → post-RA → Thumb
           (opt/flat/, 123 files)             (opt/ssa/, 57 files)
```

Driven by a **pass pipeline table** (`source/opt/engine/pipeline_table.c`), not
a hardcoded call sequence. Every pass:
- is registered with a name (`ssa:branch`, `loop:licm`, …)
- has a `flag_offset` gating it, so `-fno-<flag>` disables it
- can be killed at runtime with `TCC_DISABLE_PASS=<name>` — **which is how a
  miscompile gets bisected to a single pass without rebuilding**

### What is in there

Loop work on flat IR (deliberately, before SSA): rotation, LICM, re-rolling,
unrolling, IV strength reduction, decrement-to-zero, constant simulation,
guard elimination, pointer-IV exit substitution.

SSA work: SCCP, copy propagation, GVN, VRP, known-bits, reassociation, strength
reduction, load CSE, phi simplification, dead-loop elimination, branch folding.

Memory: alias analysis, memory-SSA, DSE, store forwarding (`sl_forward.c` alone
is 3,296 lines), byte-store merging, struct-copy round-trip elimination,
memmove→indexed-stores.

ARM-specific: MUL+ADD→MLA fusion, barrel-shift folding, LEA folding, addressing
mode fusion, `switch`→data-table conversion.

Interprocedural (within a TU): function purity, write summaries, dead statics,
noreturn propagation, constant propagation into calls.

### The DSL

`source/opt/framework/` — a declarative pass DSL (`OPT_GEN`) so a peephole is a
pattern rather than 200 lines of hand-written IR walking. PR #10 retired the
legacy hand-written loop passes in favour of it.

**Honest caveat worth saying on camera:** the DSL is size-fat on the device
build. The optimizer is ~49% of the on-device compiler's `.text`. That is a
known, documented trade.

### Levels

`-O1` and `-O2` were re-tuned (commit `4758f26e`) to line up with GCC's flag
sets rather than being arbitrary. `-O0` is DCE-only, for correctness.
`-Os` skips fusion.

**Screen-worthy:** `armv8m-tcc -dump-ir-passes=all -O2 -c x.c` — watch the IR
change pass by pass.

## Chapter 4 — The Thumb-2 back end got taken apart

At v0.0.8 the encoder was `arm-thumb-opcodes.c` (2,940 lines) + `arm-thumb-gen.c`
(2,225 lines). At v0.1.0:

- `arm-thumb-gen.c` — **15,462 lines**, the driver
- **28 `thop_*.c` encoder units**, one per instruction class: ALU-imm, ALU-reg,
  memory (imm/reg/unprivileged/exclusive), branch, block, bitfield, shift,
  multiply, DSP, coprocessor, VFP, MRS, PLD, REV, TBB, LDREX/LDAEX, ADR,
  literal loads, LDRD…

Each encoder walks instruction variants **narrow → wide** and takes the first
whose constraints hold — that is where 16-bit encoding selection happens.

And each one has a matching test file: `tests/unit/arm/armv8m/test_thop_*.c`,
totalling ~10,000 lines of encoder unit tests.

**Screen-worthy:** `thop_alu_imm.c` next to `test_thop_alu_imm.c`. It reads like
a spec.

## Chapter 5 — Floating point in hardware (PRs #10, #11)

Two orthogonal knobs, which is the right design and worth explaining:

| Flag | Values | Meaning |
|---|---|---|
| `-mfloat-abi=` | `soft`, `softfp` (default), `hard` | how FP crosses a call boundary |
| `-mfpu=` | `none`, `fpv4-sp-d16`, `fpv5-sp-d16`, `fpv5-d16`, `rp2350` | which unit may be used *inside* a function |

**The hard-float ABI is complete**: floats in `s0-s15`, doubles in `d0-d7` with
AAPCS back-filling, VFP spills via `vldr`/`vstr`, and `.ARM.attributes`
(`Tag_FP_arch`, `Tag_ABI_HardFP_use`, `Tag_ABI_VFP_args`) matching
`arm-none-eabi-gcc` **byte-for-byte**.

**The RP2350 DCP** (`-mfpu=rp2350`): the RP2350 has no double-precision FPU, but
it does have a "double coprocessor" on CP4. The compiler emits inline DCP
sequences for `double` add/sub/compare. Four matching runtime libraries ship
(`libsoftfp`, `libvfpv4sp`, `libvfpv5dp`, `librp2350fp`).

Nice detail for the video: **AAPCS-VFP passes doubles in `d0-d7` even on a
single-precision-only FPU.** The ABI says where arguments live, not which
arithmetic exists — so the callee unpacks `d0` into a GPR pair to call
`__aeabi_dadd`. That is the kind of thing you only find by running it.

Measured limit worth being upfront about: **the DCP flushes subnormals to zero**
in compare and `d2f`, and has no path that doesn't. The conformance runner takes
`--allow-ftz` for that configuration only; the soft-float baseline stays held to
full IEEE-754.

Still on the list: `float` compares/converts/negate still call `__aeabi_*`;
no native `vadd.f64`; DCP `dmul`/`dneg` not inlined yet.

## Chapter 6 — Correctness infrastructure (PR #8 and throughout)

This is the half of the work that does not show up in a feature list, and it is
arguably the more impressive half.

**`tests/ir_tests/` — 569 C programs**, compiled and run under QEMU, pytest-driven.
This is the primary suite and did not exist at v0.0.8.

**GCC torture tests** — `gcc.c-torture` fetched on demand (sparse checkout, ~16 MB
rather than the 1.3 GB gcc repo), split into compile and execute phases.

**Fuzzing** — `tests/fuzz/gen_c.py` is a **seedable, UB-free random C generator**.
The UB-freedom is the point: both oracles (O0/O1/O2 self-consistency, and
tcc-vs-gcc) treat any output divergence as a candidate miscompile, so a program
with UB would produce false positives. Every overflow-capable operation is done
on `unsigned`, every shift count is masked. Then:
`scripts/reduce.py`, `reduce_divergence.py`, `triage_seed.py` shrink a failing
seed to a minimal repro.

**Golden IR tests** — per-pass IR dumps snapshotted against checked-in
`.expected` files. A pass that changes its output has to say so.

**AddressSanitizer is ON by default** in `./configure`. You have to
`--disable-asan` to turn it off.

**Self-hosting** — `tests/selfhost/`: the compiler compiles its own sources, and
the resulting ARMv8-M binary runs on-device under YasOS.

**Host unit tests** — 205 files under `tests/unit/`, testing individual optimizer
passes in isolation, plus a coverage checker (`check_coverage_files.py`).

**Screen-worthy:** `make test -j16` scrolling, then `tests/fuzz/gen_c.py` output.

## Chapter 7 — Metrics as a first-class artifact

`metrics/` + a Grafana dashboard backed by SQLite, recording **per commit**:
code size, compile time, RP2350 cycle counts, correctness counts.

The stated motivation is good on camera:

> "so an SSA-migration commit's effect is a graph, not a guess"

CI (`.github/workflows/ci.yml`, 301 lines) runs:
- build + full test suite in a container
- the float-ABI matrix (`softfp`, `hard`) against matching multilib
- golden-IR snapshots
- code size measured on a fast cloud runner…
- …then **RP2350 performance on a real board**, via a self-hosted Raspberry Pi 5
  runner with a Pico Plus 2 attached

Plus `metrics/gate.py`, which compares a run against its parent and can fail the
build.

**Screen-worthy:** the Grafana dashboard. If there is one shot that sells "this
is a serious compiler project", it is that one.

## Chapter 8 — Where it actually stands vs GCC

From `docs/plans/o2_size_and_speed_levers.md`, measured on this tree, 4,151 tests
/ 20,435 functions compared against `arm-none-eabi-gcc -O2`:

| | |
|---|---|
| TCC / GCC instructions | 696,942 / 648,284 = **1.08x** |
| Functions where TCC is **better** | 7,839 (−80,811 instructions) |
| Functions where TCC is worse | 9,748 (+129,446) |

Per suite the spread is wide — `gcc-execute` is **1.00x** across 16,308
functions, while the hand-written `ir` suite is 2.06x. Later rounds in that
document bring the corpus ratio to **1.05x**.

The author's own analysis is the honest bit: the aggregate 1.08x "flatters us —
it nets a large win on one side against a large loss on the other," and
`main` alone accounts for 47% of the gross excess.

Encoding width is *not* the systemic gap (TCC 33.9% wide encodings vs GCC 31.6%).
The gap is instruction count.

## Chapter 9 — YasOS integration

- **YAFF output** (`source/obj/tccyaff.c`, 1,416 lines) — a flat
  position-independent module format for the YasOS loader, selected with
  `-Wl,-oformat=yaff`, for executables and shared libraries alike
- The YasOS target defaults to **PIC with text/data separation**, shared
  read-only `.rodata`, and **SB-relative GOT addressing**
- `-ffunction-sections` + `--gc-sections`, frame-pointer elimination,
  de-inlining — all landed to shrink the on-device compiler's `.text`
- The compiler builds for ARMv8-M and **runs on the device**, so the same
  sources produce both the host cross compiler and the on-target one

Consequence on the OS side: the legacy Python ELF→YAFF converter
(`dynamic_loader/elftoyaff/mkimage/`, ~3,000 lines) was **deleted** in v0.1.0.
The compiler emits the format directly, so the conversion step stopped existing.

### Demos that will land

### Things to say that are true and unusual

- The optimizer is bigger than the rest of the compiler.
- ASAN is on by default; you opt out for production.
- The fuzzer is UB-free *by construction* — that's a design decision, not a
  detail.
- CI measures cycles on a real Pico Plus 2, not an emulator.
- The compiler self-hosts on a Cortex-M33 with 520 KB of SRAM.
